# Spring AI 2.0 重构设计 - 工具治理系统

## 1. 重构目标

将当前基于自定义拦截器链的工具治理系统迁移到 Spring AI 2.0 的 Advisor 架构，主要针对5个拦截器模块：
1. AuditInterceptor - 审计日志
2. PermissionInterceptor - 权限校验
3. ValidationInterceptor - 参数校验
4. ConfirmationInterceptor - 二次确认
5. TimeoutRetryInterceptor - 超时重试

## 2. 为什么要重构

### 当前问题
你提到现有实现"写得太乱"，具体体现在：

1. **包装层级过多**
   - `AiAssistantController` → `ToolMonitorConfig.wrapTools()` → `ObservableToolCallback` → `ToolExecutor` → 拦截器链
   - 调用路径不直观，需要在多个类之间跳转才能理解完整流程

2. **自定义拦截器链与 Spring AI 的工具调用机制脱节**
   - `ObservableToolCallback` 手动包装每个工具
   - `ToolExecutor` 递归构建拦截器链
   - 这些都是重复造轮子，Spring AI 2.0 有原生解决方案

3. **事件发射和拦截器混杂**
   - `ObservableToolCallback` 既负责发射前端事件，又负责调用拦截器
   - 职责不清晰

### Spring AI 2.0 的优势

根据 [Spring AI 2.0 官方文档](https://spring.io/blog/2026/06/15/spring-ai-composable-tool-calling) 和搜索结果：

1. **Advisor Chain 模式**
   - 官方支持的拦截器机制，类似你现在的拦截器链
   - `ChatClient` 自动运行有序的 Advisor 链
   - Advisor 可以嵌套、组合、重新进入下游链

2. **ToolCallingAdvisor**
   - 2.0 内置的工具调用生命周期管理
   - 自动处理工具循环（loop until no tool calls）
   - 替代了 1.0 中每个模型自己实现的工具循环

3. **清晰的架构**
   - 拦截、修改、增强 AI 交互的标准方式
   - 可以观察和流式传输中间事件
   - 更符合 Spring 生态的设计模式

## 3. 重构范围

### 3.1 需要改动的模块

| 模块 | 当前实现 | 重构后 |
|------|---------|--------|
| **拦截器** | 5个自定义 `ToolInterceptor` 实现 | 5个自定义 `Advisor` 实现 |
| **拦截器链** | `ToolExecutor` 递归构建链 | Spring AI 2.0 的 `AdvisorChain` |
| **工具包装** | `ObservableToolCallback` 手动包装 | 移除，使用 Advisor |
| **配置** | `InterceptorChainConfig` 返回 `List<ToolInterceptor>` | `AdvisorConfig` 返回 `List<Advisor>` |
| **控制器** | `ToolMonitorConfig.wrapTools()` | 直接注册 Advisor 到 `ChatClient` |

### 3.2 不需要改动的模块

| 模块 | 保持不变的原因 |
|------|---------------|
| **配置类** | `ToolGovernanceProperties` - 配置结构与拦截实现无关 |
| **上下文** | `ToolExecutionContext` - 可以在 Advisor 中复用 |
| **异常类** | 所有 `com.dataplatform.ai.exception.*` - 业务逻辑不变 |
| **服务层** | `ConfirmationService`, `PermissionService` - 业务逻辑不变 |
| **数据模型** | `ToolAuditLog`, `ToolConfirmation` 等 - 数据结构不变 |
| **工具类** | `DataSourceTool`, `FaqTool`, `JobTool` - 工具本身不变 |

## 4. 技术方案

### 4.1 核心架构变化

#### Before (Spring AI 1.0)
```
用户请求
  → AiAssistantController
  → ToolMonitorConfig.wrapTools()
  → ObservableToolCallback (包装每个工具)
  → ToolExecutor.execute()
  → 自定义拦截器链 (AuditInterceptor → PermissionInterceptor → ...)
  → delegate.call() (实际工具调用)
```

#### After (Spring AI 2.0)
```
用户请求
  → AiAssistantController
  → ChatClient (配置了 Advisor Chain)
  → Spring AI 内置的 AdvisorChain
  → 自定义 Advisor (AuditAdvisor → PermissionAdvisor → ...)
  → ToolCallingAdvisor (Spring AI 2.0 内置)
  → 实际工具调用
```

### 4.2 Advisor 实现模式

每个拦截器转换为 Advisor 的模式：

```java
@Component
public class AuditAdvisor implements CallAdvisor {
    
    @Override
    public AdvisedRequest adviseRequest(AdvisedRequest request, Map<String, Object> context) {
        // 前置处理：记录开始时间、提取参数
        context.put("audit_start_time", System.currentTimeMillis());
        return request;
    }
    
    @Override
    public ChatResponse adviseResponse(ChatResponse response, Map<String, Object> context) {
        // 后置处理：记录结束时间、保存审计日志
        long startTime = (long) context.get("audit_start_time");
        long duration = System.currentTimeMillis() - startTime;
        
        // 保存审计日志
        saveAuditLog(response, duration);
        
        return response;
    }
}
```

### 4.3 五个拦截器的迁移策略

#### 1. AuditInterceptor → AuditAdvisor
- **功能**: 记录工具调用的审计日志
- **迁移难度**: ⭐ 简单
- **实现**: 
  - `adviseRequest`: 记录开始时间、用户ID、工具名、参数
  - `adviseResponse`: 计算耗时、记录结果、保存到数据库

#### 2. PermissionInterceptor → PermissionAdvisor
- **功能**: 检查用户是否有权限调用工具
- **迁移难度**: ⭐ 简单
- **实现**:
  - `adviseRequest`: 提取工具名、检查权限、抛出异常或放行
  - 复用现有的 `PermissionService`

#### 3. ValidationInterceptor → ValidationAdvisor
- **功能**: 校验工具参数的合法性
- **迁移难度**: ⭐⭐ 中等
- **实现**:
  - `adviseRequest`: 解析参数 JSON、运行 JSON Schema 校验
  - 挑战: 需要在 `AdvisedRequest` 中获取工具定义和参数
  - 复用现有的 `ToolSchemaRegistry`

#### 4. ConfirmationInterceptor → ConfirmationAdvisor
- **功能**: 二次确认（高风险操作）
- **迁移难度**: ⭐⭐⭐ 复杂
- **实现**:
  - `adviseRequest`: 检查是否需要确认、是否已确认
  - 抛出 `NeedConfirmationException`（前端拦截）
  - 复用现有的 `ConfirmationService`
- **挑战**: 异步确认流程需要与 Advisor 架构协调

#### 5. TimeoutRetryInterceptor → TimeoutRetryAdvisor
- **功能**: 超时控制和自动重试
- **迁移难度**: ⭐⭐⭐⭐ 非常复杂
- **实现难点**:
  - Spring AI 2.0 的 Advisor 是同步的，没有原生超时机制
  - 可能需要保留部分自定义逻辑
- **两种方案**:
  - **方案A**: 在 Advisor 中用 `CompletableFuture` 包装（类似现有实现）
  - **方案B**: 使用 Spring AI 2.0 的 `RetryAdvisor`（如果有），配合自定义超时逻辑

### 4.4 事件流（前端实时更新）的处理

当前 `ObservableToolCallback` 发射 `tool_start` 和 `tool_end` 事件到前端。

重构后的方案：
```java
@Component
public class ObservabilityAdvisor implements CallAdvisor {
    
    private final Sinks.Many<Map<String, Object>> eventSink;
    
    @Override
    public AdvisedRequest adviseRequest(AdvisedRequest request, Map<String, Object> context) {
        // 发射 tool_start 事件
        eventSink.tryEmitNext(Map.of(
            "type", "tool_start",
            "toolName", extractToolName(request),
            "arguments", extractArguments(request)
        ));
        return request;
    }
    
    @Override
    public ChatResponse adviseResponse(ChatResponse response, Map<String, Object> context) {
        // 发射 tool_end 事件
        eventSink.tryEmitNext(Map.of(
            "type", "tool_end",
            "result", response.getResult()
        ));
        return response;
    }
}
```
